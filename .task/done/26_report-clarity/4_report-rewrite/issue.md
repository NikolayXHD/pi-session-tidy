# 4 — Переписывание докладов

Цель: доклад длиннее порога N переписывается яснее по правилам изложения из
контекста сессии.

Способ: подзадача берёт финальные доклады — реплики без tool calls;
промежуточные сообщения между tool calls не обрабатываются. Результат пишется
в сессию записью custom entry и при перезапуске восстанавливается. Приёмка —
обёртка результата и отсутствие tool-разметки. Длина — не критерий: доклады не
сжимаются, улучшенная формулировка может быть длиннее исходной (правило
@NikolayXHD).

Проверка: сценарий TESTING.md для живой сессии; пробник покрывает отбор
докладов и приёмку результата.

## Итог

Сделано @pi-agent: отбор финальных докладов (`selectReports`, без tool calls,
длиннее `minReportTokens`), переписывание через общую очередь с конспектами в
порядке следования сессии (`orderWork`), приёмка по форме без критерия длины
(`validateReport`), запись `session-tidy-report-applied` с восстановлением при
перезапуске. Подмена текста в модельном контексте — через ту же карту
подмен, что и конспекты.

Проверено: `node src/probe.mjs` — 114 passed; живая сессия — см. ниже.

## Правка: только проблемные доклады

@NikolayXHD: доклады не переписывать, если нет проблем; правки должны быть
ценными. Счётчик переписанных докладов несёт ценность как сигнал качества
основной модели только при переписке проблемных текстов.

Сделано @pi-agent: строгий формат двух знаков, как у реплик (`<unchanged/>` —
переписывать нечего, `<rewrite>…</rewrite>` — переписанный текст); `reports.md`
переписан — переписывать только доклад, который мешает понять с первого
чтения; ясный доклад остаётся как написан. Счётчики считаются только
состоявшиеся замены.

Проверено: `node src/probe.mjs` — 124 passed; живой сценарий — TESTING.md,
«Clear report».
