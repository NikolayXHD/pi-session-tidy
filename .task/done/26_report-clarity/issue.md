# 26 — Заход 2: внятность докладов

## Контекст

pi-compact-thinking улучшает сессию одним способом: аккуратизация
thinking-тегов (старые рассуждения сворачиваются в конспекты). @NikolayXHD
хочет второй способ улучшения той же сессии — повышение внятности докладов.

## Желаемое поведение (@NikolayXHD)

- расширение видит реплику длиннее N (N — конфиг);
- расширение предлагает более ясную и внятную формулировку, согласно правилам
  из контекста (AGENTS.md и всё остальное);
- чтобы в этом был смысл, это должна делать другая модель (конфиг: имя модели,
  thinking level);
- подозрение @NikolayXHD: аккуратнее — сослаться на `agents/agent-name.md`, где
  .md используется расширением «вручную» просто как удобный контейнер для
  настроек модели и текста задачи;
- тогда и первый процесс (компактные thinking) можно перевести на аналогичный
  механизм настройки.

## Технические факты (сверено с типами pi 1.3.0)

- Другую модель с выбранным уровнем рассуждений расширение вызвать может:
  `ModelRegistry.find(provider, modelId)` и `streamSimple(model, context,
  options)` (pi-coding-agent), в `SimpleStreamOptions` есть `reasoning:
  ThinkingLevel` и `thinkingBudgets` (pi-ai).
- Готовую реплику видно по событию `message_end` (message_end, turn_end,
  agent_before_settle — события расширения pi-coding-agent).
- `agents/*.md` (кастомные субагенты pi-subagents) — frontmatter `model`,
  `thinking` плюс тело как текст системной задачи. Расширение может прочитать
  файл само (`readFileSync`) и использовать как контейнер; это обсуждаемый
  механизм настройки.

## Живые сценарии

Сценарий сериализации дописан в `TESTING.md` пакета («Turn serialization.») —
раньше для него описания не было. Прогнаны дочерние сессии `pi` в
`/tmp/session-tidy-check`, записи смотрел в JSONL сессии.

- **off-режим.** Ход без `/tidy`: ни одной записи `session-tidy-*` в JSONL,
  работа не стартует. После `/tidy` футер показывает счётчики (`💭`, `😞`).
- **атрибуция.** Три одинаковые громкие реплики — три записи
  `session-tidy-reply-applied` с разными `targetEntryId` (`658868bb`,
  `f620155c`, `96d5e6a5`) и одним `rawHash` для одинакового текста;
  `[rewritten reply]` стоит под своей репликой, счётчик `😞 3`.
- **сериализация.** Реплика второго хода переписана до начала следующего
  хода: запись переписки легла в JSONL до ответа следующего хода, очередь
  отработала до ухода запроса. Строгая проверка содержимого запроса —
  сценарий с логгером `before_provider_request` в `TESTING.md`.
