# Интервью 27 rewrite-observability

Протокол: вопросы по порядку, каждый обсуждается один раз. Позиции и факты —
`design.md`; здесь — формулировка вопроса, позиция и решение. Ответы
записываются по мере обсуждения (`@NikolayXHD` / `@pi-agent`).

## Вопросы на старте

1. **Что такое observability в этой постановке.** Варианты: (а) артефакты на
   диске — цель `X` у каждого include-источника `X.template`; (б) отчёт кнопки
   — per-file статус записи; (в) оба. Позиция @pi-agent: (в). Артефакт —
   основное (по нему видно, что реально попало в контекст: например, блок
   `{{#if is_flash}}` в `roles/snippets/tests.md.template`); отчёт объясняет,
   что записано и почему что-то пропущено.

2. **Какой `X.template` порождает цель `X`.** Варианты: (а) каждый include,
   упомянутый в шаблонах — статическое имя, динамическое — для каждого
   значения из списка значений переменной; (б) каждый `X.template` под корнями
   include (агент-директория, `<project>/.pi`); (в) только include, достигнутые
   текущим рендером (`partialPaths`); (г) цель не писать, наблюдаемость —
   только отчётом. Позиция @pi-agent: (а). Покрывает все `roles/**`
   независимо от `view`, не обходит посторонние деревья агент-директории
   (`git/`, `sessions/`), правило остаётся предсказуемым: «у каждого
   используемого `X.template` есть `X`». Вариант (в) проще, но
   `roles/develop.md` пишется только при `role=develop` — наблюдаемость
   неполная и зависит от значения переменной.

3. **Форма отчёта кнопки.** Варианты: (а) transient-уведомление; (б) блок
   «последняя запись» в меню `/template`; (в) оба канала. Позиция @pi-agent:
   (в): уведомление подводит итог, блок в меню даёт полный список и переживает
   исчезновение уведомления.

4. **Содержание отчёта.** Статусы на файл: `written`, `unchanged`, `failed`
   (с причиной), и — если такие остаются — `include-only` (цели нет). Полный
   список файлов или только отклонения? Позиция @pi-agent: полный список —
   файлов около 15, список читается целиком и не требует досчитывать, чего не
   хватает.

5. **Git-судьба новых целей.** Варианты: (а) отслеживать в репозитории агента
   (как `AGENTS.md`); (б) `.gitignore` (как `agents/helper-flash-*.md`).
   Позиция @pi-agent: (б) — цель порождена из источника, держать оба в
   истории значит смешивать источник и производный артефакт; наблюдаемость от
   отслеживания не зависит.

6. **Уточнение по попыткам @NikolayXHD.** Что именно пробовали: нажатие
   кнопки, правка `template.json`, ожидание появления `tests.md` при другом
   `role`? Нужно, чтобы не пропустить другое ожидание к кнопке.

7. **Семантика цели include-источника.** Подтверждение: цель несёт
   отрендеренный текст (вложенные include развёрнуты), а не текст с тегами —
   как и все остальные цели. Позиция @pi-agent: отрендеренный; цель везде
   означает готовый текст.

## Принятые решения

1. Observability — оба канала: цель `X` у каждого include-источника
   `X.template` плюс отчёт кнопки со статусом записи на файл.
2. Цель порождает include, упомянутый в шаблонах: статическое имя; динамическое
   — для каждого значения из списка значений переменной. Рендер цели — под тем
   же view, что и цель включающего файла.
3. Отчёт кнопки — оба канала: transient-уведомление со сводкой и блок
   «последняя запись» в меню `/template` со списком файлов и статусами.
4. Отчёт — полный список файлов со статусами: `written`, `unchanged`, `failed`
   (с причиной), `not included` — `.template`, который никуда не включается и
   цели не порождает.
5. Git репозитория агента не трогаем: ни `.gitignore`, ни отслеживание файлов.
   Задача пишет цели на диск; что с ними делает git — вне её.
6. Вопрос снят: ожидание зафиксировано постановкой, уточнения по «попыткам» не
   требуется.
